# 一次开关是一个持有全局锁的事务

每个写盘的开关命令（`on` / `off` / `toggle` / `restore`）在读取清单之前获取一把独占 `flock`，一直持有到清单写完。锁是全局的：作用于整个状态目录，而不是每个载体一把。

## Why

一次开关是「读清单 → 比对哈希 → 渲染 → 写多个文件 → 写清单」的读-改-写事务。没有锁时，两个并发进程会各自读到同一份旧清单、各自规划，后写的那次覆盖先写的，前一次的载体条目从清单里消失——文件已经被改过，但工具失去了记录它们原始内容的能力。

锁的**位置**比锁本身更容易写错。只在 `save_manifest` 外面加锁解决不了问题：冲突窗口在读取和写入之间，两个进程仍然可以基于同一份陈旧字节做决定。所以锁必须在 `load_manifest` 之前获取。

粒度的选择：每载体一把锁的并发收益是零——用户不会同时开两个代理，而这些操作最终都要写同一份清单，因此全局锁与事务边界正好对齐，也避免了「两个进程交错修改不同载体」这种难以讲清的语义。

锁文件放在 `$XDG_RUNTIME_DIR`（不可写时回退到临时目录），**不放在状态目录里**。它是运行时协调，不是持久状态；而且 `restore` 在没有快照时承诺完全不写盘，锁文件若落在状态目录会破坏这条既有契约（实现时正是被 `tests/aggregate.bats` 抓到的）。运行时目录在注销时被清空，也顺带保证陈旧锁不会跨会话残留。

## Consequences

- 并发开关会等待，默认最多 5 秒；超时以退出码 1 结束并提示「另一个 proxysw 正在切换」。`PROXYSW_LOCK_TIMEOUT` 可覆盖，测试用它把等待压到亚秒级。
- `--dry-run` 不取锁、也不创建锁文件，因为它承诺不写任何东西。
- 锁目录的可用性用真实写探针检测：只读挂载的 `/run/user/*` 权限位看起来仍是 0700，`os.access` 无法识别，只有实际创建文件才能发现。
- 锁按状态目录的路径哈希命名，不同 `XDG_STATE_HOME` 的两个仓库不会互相等待。
- 崩溃的进程不会留下死锁：`flock` 随文件描述符关闭自动释放。
