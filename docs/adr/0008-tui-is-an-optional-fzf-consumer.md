# TUI 是可选 fzf 消费者，不是第二个写者

`proxysw tui` 用一个可选的 `fzf` 提供交互式载体选择器。它只通过 `proxysw ... --json` 子进程读取状态、预览开关计划并应用开关；不 import 引擎、不直接写载体文件，也不复制快照、冲突检测或原子写入的逻辑。

## Why

开关的领域里有六个载体和一份清单，但日常使用只需要「看见开关状态，挑载体，执行一次开关事务」。完整状态表很宽，混合状态下还要拼载体名；一个键盘驱动的选择器解决的是这个操作问题，不是「常驻监控」问题。

fzf 是唯一新增的外部程序，而且只影响 `tui` 这一条路径：核心命令仍然只依赖 Python 标准库，fzf 缺失时以用法错误退出。TUI 通过 CLI 的 `--json` 文档消费状态和计划，因此仍然只有一个写者、一份契约和一套冲突/锁语义；测试也可以用 stub fzf 在无终端的环境里覆盖逻辑。

## 考虑过的替代方案

- **标准库 curses 面板**：零外部依赖，但 6 行数据用不上常驻面板，代码量和 pty 测试成本高一档。
- **Textual**：控件最好，但需要 pip 依赖、打包/安装方式和新的测试栈，和「不是 Python 包、没有构建步骤」冲突。
- **Go/Rust 独立二进制**：第二套工具链和编译产物，对 6 行数据是过度设计。
- **仓库外脚本**：不进入安装、测试和文档，用户得不到「装一次就可用」的 TUI。

## Consequences

- `tui` 不接受 `--json`/`--dry-run`/`--force`/`--verbose`/`--check`/`--shell`；`--json` 的「所有命令」措辞改为「非交互命令」。
- 首版只做查看与开关；`restore`、冲突 `--force`、端点/`no_proxy` 编辑仍走 CLI。
- 不新增 JSON 字段，schema 保持 2；TUI 只消费现有 `status` 与开关文档。
- fzf 只用长期存在的选项，不设版本下限；测试用 stub fzf，真实渲染靠人工冒烟。
- 打开选择器总是执行 `status --check --json`，因此看到的是打开时刻的最新状态。探测是一次 ≤0.5 秒的本地 TCP 连接（不写字节、不发 HTTP 请求）；`--proxy` 同时作用于探测、dry-run 和 apply。端点 `down` 只是警告，不阻塞选择或开关：用户可以先准备好载体，再启动代理。
- fzf 的查找顺序是 `PROXYSW_FZF` 指定的路径，否则 `PATH`；两者都没有时 `tui` 以用法错误退出。`PROXYSW_FZF` 也用于测试里模拟缺失。
- TUI 是独立进程：逐载体结果走 stdout，确认行、提示和错误走 stderr；它不复用 CLI 的 `context.info`/`progress`/`emit_document` 通道。结果行里的「已写」以 apply 文档的 `written` 为准，`changed` 只表示计划想改。
- TUI 一次确认只发起一次写盘开关调用；多选仍是一个开关事务，不逐载体翻转。
